# ABI-v4 upstream sync startup regression and prefix handoff

## Situation

The first ABI-v4 upstream-sync candidate crashed before the launcher could show
its spinning dots. The shared failure across Oblivion and Fallout: New Vegas was
in wineserver startup, before either game reached graphics or guest code.

The first failure mapped to `fatal_error -> create_server_dir ->
open_master_socket -> start_inprocess_server`: wineserver's separate PRX libc
had no usable environment, then rejected its fallback home directory. Patch
0739 copied ntdll's `environ` pointer to wineserver. That emitted
`environment handoff entries=15 prefix=set`, but the next run still took
`create_server_dir`'s HOME fallback. The exact return PC mapped to the `home[0]
!= '/'` fatal branch. The startup environment log therefore did not prove that
`create_server_dir` consumed the prefix.

## Full ABI-v4 startup-chain audit (2026-11-04)

A direct source comparison against the Oct 30 complete server-start chain in
`docs/HANDOFF-2026-10-26.md` found that the ABI-v4 candidate did **not** carry
all of the known PS4 fixes. The earlier claim that the 0734–0738 and
0742–0747/0771 chain was present was incorrect. This check compared the actual
Wine source used by the package at
`/home/zpeirce/codex_scratch/abi4-upstream-port-20261104/build/wine-ps5/source`,
not just patch filenames.

### Confirmed present or equivalent

- `0736`–`0738`: in-process client descriptor handoff and descriptor-number
  transfer are present in `server/request.c` and NTDLL.
- `0739`–`0741`: current candidate has the environment handoff, explicit
  prefix argument, and PS4 directory-identity handling.
- `0866`: current NTDLL source guards the request-pipe close on PS4.
- `0871`: current mapping code installs `mapping_fd_ops` for ownerless mapping
  fds.
- `0112`: restored in the current package stage; skips the PS4 prefix owner
  check.

### Confirmed missing from the ABI-v4 source

- `0734`: `server/fd.c::dup_fd_object()` still relies on `dup()` and has no
  reopen-by-name fallback.
- `0735`: `server/mapping.c::mapping_init()` still relies on `dup_fd_object()`;
  it does not take/share the original mapping fd and clear the stale error.
- `0742`: `server/thread.c` still directly treats `fcntl(F_SETFL, O_NONBLOCK)`
  failure as fatal in `new_thread()` and `init_thread()`; there is no PS4
  `pw_set_nonblocking()` helper.
- `0743`: `ntdll/unix/env.c::get_initial_environment()` still iterates
  `environ` without a null check.
- `0744`: `ntdll/unix/virtual.c` still maps the user shared-data section using
  Wine's 4 KiB `page_size`, without the PS4 host-page rounded mapping.
- `0745`: NTDLL still sets `needs_close` from the fd-cache path and closes the
  returned fd in error paths; PS4's shared server/client descriptor ownership
  is not respected.
- `0746`: `build_initial_params()` still invokes `run_wineboot()`; there is no
  PS4 path to signal completion for the already-booted copied prefix.
- `0747`: `get_image_address()` still calls `getauxval(AT_PHDR)` under
  `HAVE_GETAUXVAL` on Prospero instead of returning no image address.
- `0771`: `inprocess_wake_poll_event()` still drains with an unbounded
  `while (read(...) > 0)` even though the PS4 cannot set the wake pipe
  nonblocking.

### Diagnostics, not additional functional fixes

- `0113` fatal-error-to-klog is absent. This would expose the reason for
  `fatal_error()` exits that currently disappear from console logs.
- `1033` carries the `0865` protocol-error klog diagnostic in the latest
  package. The latest SIGSYS did not emit a protocol-error line, so it did not
  explain that failure. Do not treat diagnostics as substitutes for the
  functional fixes above.

The latest tested package (`5d119146...`) therefore is **not** a complete
rebase of the known-good startup fixes. Do not spend another install/launch on
it. The next package should carry the confirmed missing functional patches as
one consolidated change, retain 0112/0736–0741/0866/0871 plus relocation and
all shared runtime payloads, and include 0113 only as bounded diagnostic
instrumentation. Before packaging, verify each behavior in the resulting
source and compare the final stage against the current package so unrelated
payloads do not change.

## Signal-mask ABI correction and single-run candidate (2026-11-05)

The `PW_NATIVE_FRAME` trace showed an initially unblocked SIGWINCH becoming
blocked after `pthread_sigmask(SIG_UNBLOCK, ...)` returned success. The PS4 SDK
header exposed Linux mask-operation values (`SIG_BLOCK=0`, `SIG_UNBLOCK=1`,
`SIG_SETMASK=2`), while the PS4 kernel follows the FreeBSD operation ABI
(`SIG_BLOCK=1`, `SIG_UNBLOCK=2`, `SIG_SETMASK=3`). Passing `1` therefore asks
the kernel to block the signal. This explains the exact observed state:
`old_blocked=0`, `now_blocked=1`, `pending=1`, `hits=0`. The corresponding
FreeBSD definitions are in [sys/signal.h](https://cgit.freebsd.org/src/tree/sys/sys/signal.h?id=5f438dd3acba47e54e63b13bfff31a49bcc6ddea). Max's prior raw-syscall probe already measured
signal delivery and frame setup on this console; this mismatch is in the Wine
libc call's operation argument, not a need to repeat broad signal-provider
experiments.

`mesa-build/orbis-compat/include/signal.h` now translates those three operation
constants, and `src/wine-platform-patches-ps4/0002-orbis-compat-use-freebsd-signal-numbers.patch` carries the change into rebuilds. The Wine signal object was rebuilt
with the PS4 compiler. Its disassembly shows the unblock request uses `2` and
the set-mask query/restore use `3`. The full PS4 PRX stage was then rebuilt.
