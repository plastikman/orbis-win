## Current finding

The Fallout New Vegas gameplay screenshot showed large missing black textures.
The active PS4 log `build-ps4-logs/ps5log-20261028-085250.log` records repeated
failures during D3D9 texture initialization:

```text
map_file_into_view unaligned shared mapping ... not supported
virtual_map_section mapping ... failed
```

This gives a direct mechanism for missing textures. The existing 0602 fix
handles unaligned writable shared sections while mapping PE images; the failing
call here goes through the general `virtual_map_section()` file mapping path.
The log's guest address is only Windows-page aligned, not host-page aligned.

## Patch and intended scope

Added `src/wine-patches-ps4/1024-ntdll-private-copy-unaligned-committed-mappings.patch`.
For an unaligned writable view, it keeps the current rejection for persistent
file mappings. For `SEC_COMMIT` pagefile-backed views only, it allows Wine's
existing `mprotect` + `pread` path to populate a process-local copy. This avoids
changing aligned mappings or shared writes to persistent files. The new log
line is `unaligned committed mapping ... using private copy`.

Hardware confirmation is still pending. On the next Fallout NV launch, check
that these mappings report the new private-copy line and that the paired
`D3D9: InitTexture: map failed` / D3DX texture-creation failures stop. Revisit
the section flags if the current errors continue on `SEC_FILE` mappings; do not
broaden the fallback to persistent files without evidence.

#### Allocation path trace follow-up

Source trace completed for the common DXVK failure. In both the 1079 V.A.T.S.
run and 1081 gameplay run, the failed object is a 1920x1080 D3D9 depth/stencil
surface (`D3D9Format::D24S8`, numeric `0x4b`, usage `0x2`). DXVK maps this to
`VK_FORMAT_D32_SFLOAT_S8_UINT` (`0x82`) on this device because D24S8 is not
reported natively supported. Its allocation request is 83,755,016 bytes,
32-KiB aligned, with Vulkan memory types 0,2,3,5. This is the Vulkan image
memory requirement, not simply the 1920x1080 pixel payload; the captured
diagnostic does not print the sample count.

The failure chain in the shipped DXVK 2.6.2 sources is:

1. `D3D9CommonTexture::CreatePrimaryImage()` calls DXVK image creation.
2. `DxvkMemoryAllocator::createImageResource()` gets the image requirements and
   tries dedicated allocation or pool allocation.
3. `allocateDeviceMemory()` calls `vkAllocateMemory` (retrying after releasing
   empty chunks); eligible types fail, so the allocator returns no allocation
   and emits `Memory allocation failed`.
4. Image creation returns an image without backing storage. The active
   diagnostic7 D3D9 guard logs this and throws `DxvkError`; it does not create
   or repair the missing storage.

Thus both events share a demonstrated D3D9 texture allocation failure at the
Vulkan boundary. The later game null-vtable fault is not yet proven to be caused
by that failure: V.A.T.S. faulted immediately inside D3D9 on a null object,
while gameplay continued presenting for about nine seconds before
FalloutNV.exe faulted in its recurring null-vtable helper.

RADV's PS4 `vkAllocateMemory` path then calls `radv_bo_create()` and the AMDGPU
winsys. PS4 BO backing allocation itself is a no-op against the pre-reserved
direct-memory arena. The remaining driver-side refusal points include
bookkeeping/host allocation, VA-range reservation, and mapping/protection of
that range. The captured logs do not include a matching `out of device VA`,
`sceKernelMprotect`/grant-access, or other RADV failure-stage record, and DXVK
discards the individual `VkResult` codes from its retry loop. Therefore these
runs do not identify the low-level refusal. The budget table alone does not
prove a budget rejection: DXVK does not reject allocations based on its
