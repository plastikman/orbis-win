## Current finding

The Fallout New Vegas gameplay screenshot showed large missing black textures.
The active PS4 log `build-ps4-logs/ps5log-20261028-085250.log` records repeated
failures during D3D9 texture initialization:


This gives a direct mechanism for missing textures. The existing 0602 fix

The log's guest address is only Windows-page aligned, not host-page aligned.

## Patch and intended scope

Added `src/wine-patches-ps4/1024-ntdll-private-copy-unaligned-committed-mappings.patch`.
For an unaligned writable view, it keeps the current rejection for persistent
file mappings. For `SEC_COMMIT` pagefile-backed views only, it allows Wine's
existing `mprotect` + `pread` path to populate a process-local copy. This avoids
changing aligned mappings or shared writes to persistent files. The new log
line is `unaligned committed mapping ... using private copy`.

Hardware confirmation is still pending. On the next Fallout NV launch, check
that these mappings report the new private-copy line and that the paired
`D3D9: InitTexture: map failed` / D3DX texture-creation failures stop. Revisit
the section flags if the current errors continue on `SEC_FILE` mappings; do not
broaden the fallback to persistent files without evidence.

#### Allocation path trace follow-up

Source trace completed for the common DXVK failure. In both the 1079 V.A.T.S.
run and 1081 gameplay run, the failed object is a 1920x1080 D3D9 depth/stencil
surface (`D3D9Format::D24S8`, numeric `0x4b`, usage `0x2`). DXVK maps this to
`VK_FORMAT_D32_SFLOAT_S8_UINT` (`0x82`) on this device because D24S8 is not
reported natively supported. Its allocation request is 83,755,016 bytes,
32-KiB aligned, with Vulkan memory types 0,2,3,5. This is the Vulkan image
memory requirement, not simply the 1920x1080 pixel payload; the captured
diagnostic does not print the sample count.

The failure chain in the shipped DXVK 2.6.2 sources is:

1. `D3D9CommonTexture::CreatePrimaryImage()` calls DXVK image creation.
2. `DxvkMemoryAllocator::createImageResource()` gets the image requirements and
   tries dedicated allocation or pool allocation.
3. `allocateDeviceMemory()` calls `vkAllocateMemory` (retrying after releasing
   empty chunks); eligible types fail, so the allocator returns no allocation
   and emits `Memory allocation failed`.
4. Image creation returns an image without backing storage. The active
   diagnostic7 D3D9 guard logs this and throws `DxvkError`; it does not create
   or repair the missing storage.

Thus both events share a demonstrated D3D9 texture allocation failure at the
Vulkan boundary. The later game null-vtable fault is not yet proven to be caused
by that failure: V.A.T.S. faulted immediately inside D3D9 on a null object,
while gameplay continued presenting for about nine seconds before
FalloutNV.exe faulted in its recurring null-vtable helper.

RADV's PS4 `vkAllocateMemory` path then calls `radv_bo_create()` and the AMDGPU
winsys. PS4 BO backing allocation itself is a no-op against the pre-reserved
direct-memory arena. The remaining driver-side refusal points include
bookkeeping/host allocation, VA-range reservation, and mapping/protection of
that range. The captured logs do not include a matching `out of device VA`,
`sceKernelMprotect`/grant-access, or other RADV failure-stage record, and DXVK
discards the individual `VkResult` codes from its retry loop. Therefore these
runs do not identify the low-level refusal. The budget table alone does not

#### External root-cause lead: module-loader re-protection of released eboot RELRO

Max supplied a measured explanation for the F3/FNV low-address permission
failures. The PS4 module loader re-applies module 0's `PT_SCE_RELRO` protection
on every PRX or sysmodule load, even after the eboot mapping has been released.
It applies read-only permissions to whatever mapping occupies that virtual
range at load time; it does not overwrite bytes. This can revoke execute or
write access from later low-address Wine/game mappings. Max verified the
behavior with a non-Wine probe and a 1 ms permission watcher, then verified
that a stub eboot without `PT_SCE_RELRO` prevents the reset. His fixed-base
32-bit probe ran at `0x00400000` without protection repairs after module loads.
The translator probe also showed the same loader behavior, so this mechanism
is not specific to native WoW64.

Evidence and tested implementation are in the local review checkout
`/home/zpeirce/codex_scratch/max-ps4-wine-review`, especially
`docs/ps4/LOG.md` entries L23-L27, `docs/ps4/HANDOFF-i.md`,
`third_party/prospero-win/tools/pw_stub_orbis.ld`, and
`third_party/prospero-win/tools/orbis_stub_norelro.py`. Max's linker layout
places `.data.sce_process_param` first in the RW segment, folds
`.data.rel.ro` into `.data`, and keeps text/rodata in one RX segment. The
converter validates the layout and changes `PT_GNU_STACK` into the empty
`PT_GNU_RELRO` required by pinned `create-fself` v0.5.4; `create-fself` then
drops it, yielding an eboot with no `PT_SCE_RELRO`. Its output is checked.

Our current relocatable stub **does contain** `PT_SCE_RELRO`: in
`build/wine-app-relocatable/stub.oelf`, it spans image-relative
`0x9c000..0xac000` (64 KiB, read-only), or approximately
`0x49c000..0x4ac000` when loaded at `0x400000`. This overlaps the low address
space later reused by Wine. That makes the existing exec-migration history
consistent: disabling migration while retaining the old RELRO stub leaves
pages read-only, so the previous no-migration failures did not test the new
root cause.

#### Follow-up: retain module 0's data after releasing low code

Max found that `sceKernelGetModuleList` in libkernel reads module 0's data
segment after the eboot's low code range is released. Leaving the data unmapped
can crash a 64-bit process; fixed-base 32-bit titles at `0x400000` had survived
by reading their own mapped bytes there. The RW segment must remain mapped at
`0x7fff0000`, Windows' 64 KiB no-access region, while the low RX segment is
released. The data address is within 2 GiB of the code for the SDK's
32-bit-relative relocations.

The follow-up uses Max's updated linker/converter at commit
`6394f19f74e1ff0f845c153a0cf41d3196642c51`. Our stub initially could not fit
its RW segment in that 64 KiB window: the executable link whole-archived
`liborbis-compat.a`, bringing in a 442,752-byte `carve` BSS object. The eboot
does not need that archive, so the no-RELRO eboot-only link now omits it. The
resulting RW segment is `0x1060` bytes and fits wholly in the reserved window.
The tracked no-RELRO build path checks the linked ELF and final OELF layout:
RX stays below `0x55c000`, RW lies in `[0x7fff0000,0x80000000)`, no load segment
occupies the gap, and no `PT_SCE_RELRO` remains. The existing release function
unmaps only segments overlapping `0x400000..0x55c000`, so it releases the low
RX segment and leaves the high RW segment mapped.
