# Handoff: why no 64-bit title renders, and what is fixed

Date: 2026-11-16. Branch `hk/scene-load-on-v007` (orbis-win),
`ps4/upstream-ports` (playden-ps4). Nothing released or tagged.

## The finding

**`ps5_map_device_extensions()` in `dlls/win32u/ps5drv.c` was an empty function.**
The win32 halves of external memory, semaphore and fence were never set from the
fd halves RADV advertises, so win32u never offered `VK_KHR_external_memory_win32`
and `get_host_external_memory_type()` returned 0. DXVK saw
`khrExternalMemoryWin32 : 0` and refused every shared resource:

    err: Failed to create shared resource: VK_KHR_EXTERNAL_MEMORY_WIN32 not supported

Unity asks for one as soon as it has made its **second** D3D11 device (the feature
level 11_1 then 11_0 pair in DXVK's log, with a second `dxvk-submit` thread), then
waits for it for good. The main thread parks in `RtlWaitOnAddress` on an address
nothing ever wakes, no swapchain is created, `frames_put` stays 0.

Patch **1080** maps the six pairs, the same ones `nulldrv_map_device_extensions`
already has. Measured after it, on Risk of Rain 2 and on DXVK 2.6.2 and 3.1.1:
`khrExternalMemoryWin32 : 1`, the shared-resource error gone, the deadlock gone.

## What is NOT fixed

A second, independent blocker remains: DXVK's **first** buffer allocation fails.

    err: DxvkMemoryAllocator: Memory allocation failed
    err:   Size: 256  Alignment: 256  Mem types: 0,2,3,5
    err:   Heap 0: 671 MiB, 0 allocated   Heap 1: 1344 MiB, 0 allocated

Both heaps empty, so it is refusal and not pressure. Neither RADV's allocation log
nor win32u's `Failed to allocate memory` WARN fires, so **DXVK never calls
`vkAllocateMemory`** -- it refuses inside its own allocator. The type mask 0x2d is
exactly types 0,2,3,5. Identical on DXVK 2.6.2 and 3.1.1, so it is not a DXVK
version problem. Next probe: log inside winevulkan's PE-side `vkAllocateMemory`
thunk to see whether DXVK calls it at all.

Memory layout RADV reports:

    Heap[0] 671 MiB flags 0x0   types 2 (0x6), 5 (0xe), 6 (0xe)
    Heap[1] 1344 MiB            types 0 (0x1), 1 (0x1), 3 (0x7), 4 (0x7)

## Eliminated by measurement -- do not re-suspect

- **Patch 1075 / Leo 0964** (the alert rewrite): 4086 sends to 4086 wakes, zero
  failed slot lookups. The mechanism is sound.
- **Our whole sync layer**: every `RtlWakeAddress*` is traced; the missing wakes
  were never *issued*, not lost. `RtlWaitOnAddress`/`futex_queues` are stock Wine,
  untouched by our series.
- **The DXVK version**: 2.6.2 and 3.1.1 behave identically, before and after 1080.

## The knob is 64-bit-wide, not per title

Without `PW_PS4_EXEC_MIGRATE_RANGE_MAX=262144` both Hollow Knight and Risk of Rain
2 die in 5-6 s with hundreds of `SYSTEM_DEBUG_RUNTIME_SHADOW_MEMORY_ALLOC_ERROR`
(RoR2: 504). It should default on for `pe64` guests; today it is a per-game setting
nobody would know to set, so any 64-bit title a user installs dies instantly with
no clue why.

## Diagnostics added, all gated

- **1077** thread creation, **1079** alerts sent and waited for: both behind
  `PW_PS4_GUEST_SAMPLER` (they logged 40 and 4086 lines per run unconditionally).
- **1078** makes the wait watchdog signal the wedged thread, so the 64-bit sampler
  lands on it. `dump_guest_stack()` only ever worked for 32-bit guests: it reads the
  WoW64 CPU area and requires `IMAGE_FILE_MACHINE_I386`, which is why every 64-bit
  title has been invisible.
- The glue sampler's caps were raised and its stack walk now accepts guest PE
  ranges; it only took this port's PRX range before, so DXVK and UnityPlayer frames
  were filtered out.
