## Review and fix (afternoon, Claude): Vulkan root cause, diagnostics, and an EBOOT gate failure

### Root cause of the Vulkan launcher return (all DXVK titles, not just GTA IV)

The ABI-v4 Wine series dropped archive patch
`src/wine-patches-ps4/0878-win32u-ps5-a-headless-surface-on-ps4.patch`. The
ABI-v4 series already uses number 0878 for a different patch
(`0878-crypt32-ps5-root-certificates-beside-the-runtime.patch`), so the PS4
patch was lost to a numbering collision. Without it, `ps5drv.c` maps
`VK_KHR_win32_surface` only from `VK_KHR_display`. The PS4 host instance
offers `VK_EXT_headless_surface`, not `VK_KHR_display`. As a result the PE-side
WineVulkan never advertises `VK_KHR_win32_surface`, and `vkCreateInstance`
returns `VK_ERROR_EXTENSION_NOT_PRESENT` in its client-extension loop
(`dlls/winevulkan/loader.c:398-400`). This happens *before* the Unix call.
DXVK cannot create an instance, and the game exits normally.

Log evidence (`ps5log-20261104-065340.log`):
- **Every GLDS10043 run:** the client extension list omits
  `VK_KHR_win32_surface`. "Enabling 4 client instance extensions" prints
  only three names, then `DllMain …, 0, 00000001` (process detach). The 01.02
  `PW_GTAIV_VK_CREATE_INSTANCE enter` marker sits after that loop and can
  never fire; `PW_GTAIV` occurs 0 times in the log.
- **1090 at 11:32/11:33:** lists all four extensions, then reaches
  `thunk32_vkCreateInstance` and `win32u_vkCreateInstance`.
- The 10:44/10:45 runs of the original candidate (before any i386 WineVulkan
  rebuild) show the same omission, so the instrumentation did not cause it.

Corrections to the earlier notes in this file:
- **Prefix DLL swaps were no-ops.** Wine loads the built-in WineVulkan from the
  package's `lib/wine` directory, not from the prefix copies. The
  `vkGetInstanceProcAddr` offset from the DLL base is +0x1d6d0 in every 1090
  run, whatever the prefix held. In ABI-v4 runs it follows each package
  rebuild: +0x84920, then +0x84960 (01.01), then +0x849c0 (01.02). The
  "mixed-ABI" 11:29–11:35 run was therefore a clean 1090 native run, and it
  rendered.
- **"No PW_EXCEPTION32 record" is meaningless on these ABI-v4 packages.** Their
  i386 `kernelbase.dll` contains 0 `PW_EXCEPTION32` strings (1090 has 33). The
  diagnostic patches 0965/0973/1007 were also lost to number collisions.

### Blocking gate: no ABI-v4 package has run the relocation path

Every ABI-v4 session in the active log fails the same way: app module
`0xe07e`/`0xa07e`/`0x7e`, no `build_marker`, no `relocatable eboot release`,
and `400000-4a4000 is "executable"`. Every 1090 session shows module `0x7f`
and `relocatable eboot release status=0`.

The cause is the EBOOT. 1090 ships the 56,288-byte no-RELRO stub
(`5e6819e5…`), which loads `/app0/sce_module/relocated_wine_app.prx`. Every
ABI-v4 stage ships a 749,760-byte `eboot.bin` (`710ea754…`) that never
references `relocated_wine_app.prx`. The PRX is packaged, contains both
markers, and is never loaded.

The Nov. 4 notes call that 749,760-byte file "the corrected relocatable
EBOOT". They base this on an earlier launch rejection (`0x80020002`), but
that rejection came from a packaging error (the stage `eboot.bin` was passed
as an extra file, overriding `--eboot`), not from the stub design. This
violates AGENTS.md's "relocation fix in every package" rule. Resolve it before
packaging the headless candidate.

### Relocation restored: GLDS10043 APP_VER 01.03 "Orbis Wine ABI-v4 Headless Reloc" (built, not yet uploaded)

**EBOOT fix.** The stub/app contract has no Wine-ABI dependency. `stub.c`
loads `/app0/sce_module/relocated_wine_app.prx`, finds
`pw_relocated_wine_start` in its `PRXDESC1` descriptor (version 1, count ≤ 8),
and the PRX calls `pw_relocated_wine_release_eboot()` before guest start. The
ABI-v4 app PRX exports both functions and carries the descriptor (version 1,
count 2 at file offset 0x11d570, same as 1090). The descriptor generator is
identical in both trees. The package therefore uses 1090's hardware-proven
stub unchanged: `eboot.bin` SHA-256 `5e6819e5…`, 56,288 bytes.

Notes on the stub builds:
- The Nov. 4 stub build (`build/wine-app-relocatable/eboot.bin`) differs
  from 1090's by only 333 header/signature bytes.
- A fresh `stub.elf` rebuild is byte-identical to the Nov. 4 one, but

the server reads. The archive patch's own text names this as the GTA IV hang.

partly built).**

### 15:35 — 01.13 crashed every title; 01.14 fixes it (create-fself .bss tail)

**01.13: Half-Life and FNV both died at `WINE wine startup:
server_init_process`.** klog:
`[rtld] reloc_non_plt:4985: idx=2030 ... ref=wineserver.prx` →

**Root cause: a latent create-fself bug, exposed by 1053's 16 bytes.**
- create-fself sizes the writable PT_LOAD as `align16(.data) + .bss`,
  leaving out `.got.plt`, which sits between them.
- So the converted segment ends ~0x610 bytes short of the real end of `.bss`.
  It worked only because the 16 KiB page rounding covered the gap.
- 1053 pushed `__cxa_new_handler` (GOT-referenced) to 0x264010, past the
  rounded end 0x264000, and rtld refused the relocation.
- Measured on wineserver:
  - ELF data LOAD: `0xe8000 + 0x17c038`
  - oelf: `0xe8000 + 0x17ba28`

**Fix (`scripts/prx-ps4.sh`, every module):**
- After create-fself, compare the ELF's writable end with the oelf's
  page-rounded end.
- If it is uncovered, relink once with a `.bss` pad object
  (`obj/<module>_bss_pad.c`), sized so the converted end lands 0x100 into a
  page; then re-check, and fail the build if still uncovered.
- A separate NOBITS section does NOT work (create-fself only counts `.bss`).
- Only wineserver needed it (1,752-byte pad). All other modules are linked
  once and stay byte-identical.
